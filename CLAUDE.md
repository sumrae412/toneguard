# ToneGuard

Chrome extension + MCP server for tone analysis. Analyzes messages for professionalism, clarity, and emotional tone before sending.

## Structure

- Root: Chrome extension (manifest v3, content scripts, popup, overlay)
- `toneguard-mcp/`: Python MCP server (FastMCP, multi-model analysis)
- `android/`: Native Kotlin Android app with accessibility service
- `sync-server/pwa/`: Progressive Web App for mobile share sheet (served from the Railway sync-server)
- `sync-server/`: Railway-hosted Node/Express + Postgres + WebSocket sync backend

- Haiku model ID: `claude-haiku-4-5-20251001`
- Build backend: `hatchling`, not legacy setuptools
- The `.env` file must be sourced into the shell for live integration tests (not just present on disk)
- **Dual code paths: MCP + extension.** Prompts/behaviors live twice — `toneguard-mcp/critics/*.md` (MCP analyzer, dev/CI only) AND extension prompt files under `prompts/` plus inline constants in `service-worker.js` (extension calls Anthropic directly, not through MCP). Any change to one must update the other.
- **Sync backend lives in 4 clients.** The same sync protocol is implemented in `src/sync/sync-client.js` (Chrome ext + PWA), `toneguard-mcp/sync.py` (MCP server, poll-only), and `android/.../SyncManager.kt` (Android). If you change the server API in `sync-server/src/index.js`, update all three. The server URL is hardcoded in each client — bump together when the Railway hostname changes.
- **Canonical taxonomies live in `shared/analysis/*.json`; clients consume but don't redefine.** `voice-strengths.json` is the source of truth for the voice-strength enum in `service-worker.js`, `sync-server/pwa/app.js`, `analyzer.py`, and `MainActivity.kt`. If you add a new client-replicated constant, promote to `shared/analysis/` and add a probe to the manifest — don't add a 5th copy.
- **Tool schemas are generated per-client from canonical `shared/analysis/*.json`, not hand-written.** `schema.json` → `prompts/analysis-tool.json` (ext, fetched via `chrome.runtime.getURL`) + `sync-server/pwa/analysis-tool.json` (PWA, same-origin fetch); `landing-schema.json` → `prompts/landing-tool.json` + `toneguard-mcp/critics/landing-tool.json` (MCP reads the generated file = single source). ## Chrome Extension Dev Loop

- **Extension reload doesn't always pick up service-worker changes.** Bump `manifest.json` version on every ship (or every meaningful reload) so you can confirm the new build is live in `chrome://extensions`.
- **`chrome.contextMenus.create` duplicate-id is a three-part bug, not one.** The `removeAll()` wrapper is necessary but NOT sufficient. MV3 fires `onInstalled` and `onStartup` close enough together that two `removeAll`/`create` pairs can interleave and re-trigger the duplicate-id error. Required fixes together:
  1. `chrome.contextMenus.removeAll(() => chrome.contextMenus.create(...))` wrapper for idempotence.
  2. **In-flight guard** (module-level boolean) so concurrent lifecycle handlers can't both enter the setup function.
  3. **Pass a callback to `chrome.contextMenus.create`** and explicitly read `chrome.runtime.lastError`, otherwise the duplicate-id surfaces in `chrome://extensions` as an unchecked runtime.lastError even when it's benign.
- **Only one clone of this repo should be loaded as an unpacked extension.** Two clones (e.g. `~/toneguard` and `~/repos/toneguard`) cause silent version skew — Chrome keeps loading whichever path was registered first, even after you bump the manifest in the other clone. If a version bump doesn't appear in `chrome://extensions` after reload, check the "Loaded from" path before debugging the build. Prefer a single canonical clone; delete the stale one. When a version bump doesn't appear after reload, enumerate ALL clones + versions + branches in one pass before debugging, then fast-forward EVERY loaded clone (a `git pull` updates only the clone you ran it in - Chrome may load the other):
  ```bash
  find /Users/summerrae -maxdepth 6 -name manifest.json -not -path "*/node_modules/*" | while read m; do
    grep -q '"name": "ToneGuard"' "$m" && echo "$(dirname "$m"): $(grep version "$m") $(git -C "$(dirname "$m")" rev-parse --abbrev-ref HEAD)"
  done
  ```
  RESOLVED 2026-07-17: the stale second clone (`/Users/summerrae/repos/toneguard`) was retired to the Trash after verifying 0 dirty files / 0 stashes / 0 unpushed commits; Chrome's "Loaded from" was confirmed as `/Users/summerrae/claude_code/toneguard`, which is now the single canonical clone. If version skew ever reappears, re-run the enumeration above — a new second clone is the first suspect. (History: validated 2026-06-19 when reload kept showing 0.4.15 because Chrome loaded the un-pulled clone.)
- **When a feature fails open, surface the degraded state on EVERY affected action, not just the first.** A one-time notice on entry into a degraded mode reads as silence on every action after it. The quota auto-pause ([PR #77](https://github.com/sumrae412/toneguard/pull/77)) shipped showing the in-page paused notice only on the FIRST pause (`just_paused`); later sends went out unchecked and looked identical to a clean pass - user reported "it just said sent, didn't say it was out of funds." Fix in [PR #78](https://github.com/sumrae412/toneguard/pull/78): all three send/review handlers in `content.js` call `showPaused()` on every `result.paused`. The toolbar badge alone is too easy to miss. Same family as "Never swallow parse errors into a destructive default" - a silent degraded path is as dangerous as a swallowed error.
- **Anthropic API exhaustion has three distinct failure shapes - classify before blocking.** `lib.js:classifyQuotaError` splits them: (a) usage-limit 400 (body matches `usage limit` / `reached your specified API usage limits`) -> `TG_LIMIT_001`; (b) credit-balance 400 (body matches `credit`, e.g. "Your credit balance is too low to access the Anthropic API") -> `TG_CREDIT_001`; (c) invalid key -> 401, not a quota class. The extension's original behavior blocked every send on any error, so a $0 balance surfaced as a total lockout under a cryptic `TG_RUNTIME_001`. Both 400 quota classes now auto-pause (fail open) and offer Resume; 401 stays a hard error. **Console billing confusion to flag to users:** "Organization credits" (prepaid balance the API draws down; triggers the credit-balance 400 at ~$0) is a DIFFERENT number from "Spend this month / of $200K limit" (a monthly ceiling, not a funded balance). Auto-reload "on" with a small reload amount can still momentarily hit $0 under bursty usage and 400.
- **Log structured errors as strings, not objects, in extension code.** `console.warn("ToneGuard:", errObj)` renders fine in DevTools but as `[object Object]` in the `chrome://extensions` error pane — the two surfaces stringify the second arg differently. Format structured errors (`{type, message, diagnostic_code}`) into a readable string like `"type [code]: message"` before logging. See `formatErrorForLog()` in `content.js` (handles null, string, object, primitive, and circular-ref cases).
- **Service-worker state is not persistent.** Chrome can terminate and re-spawn the SW at any time; top-level code (including context-menu creation) re-runs. All setup must be idempotent.
- **Claude responses are pretty-printed JSON.** Haiku 4.5 (`claude-haiku-4-5-20251001`) emits multi-line JSON. Never sanitize with a global control-char regex — it corrupts structural whitespace between `{` and the first key. Use `lib.js:parseApiResponse` (fast-path `JSON.parse`, state-machine sanitizer fallback, surfaces errors instead of silent catch).
- **JSON-returning model calls use forced tool output, not text-JSON parsing.** Every analysis-pipeline call (ext main analysis + landing critic, MCP `analyzer.py` Claude sites, GPT via JSON mode) forces a tool call and reads the parsed `tool_use.input` — `lib.js:extractToolResult` / `analyzer.py:_extract_tool_result`, both falling back to the text parser on a text block (keeps text-block mocks green). This killed the `TG_PARSE_001` class from malformed model JSON (stray quotes, fences, prose). `parseApiResponse` is now only the fallback path. A `max_tokens` stop with tool use = treat the partial `tool_use.input` as `result = null` so escalation fires. PRs [#50](https://github.com/sumrae412/toneguard/pull/50)/[#51](https://github.com/sumrae412/toneguard/pull/51).
- **Never swallow parse errors into a destructive default.** If the Claude response won't parse, return `{flagged: false, error: "..."}` — never silently release the send as if the check passed. The user must see the failure.
- **For bugs the user hits and you can't,** add labeled `console.log` breadcrumbs on the critical path with a grep prefix (`[ToneGuard:diag]`) and ship as a diagnostic build. Don't theorize without runtime evidence — see `bug-fix` skill's "user can reproduce, agent cannot" sub-path.
- **`verifyInsertedText` compares via a symmetric `stripMentions`, but the editor side may be Slack-expanded (`@sam` → `@Sam Rivera`).** Any extension to the mention regex must consume trailing capitalized words on both sides — otherwise the after-side keeps a dangling surname, the substring compare silently fails, and a successful insert gets nacked. See `lib.js:451` and the regression test at `tests/lib.test.js:429`.
- **`AGENTS.md` is a verbatim mirror of `CLAUDE.md`** — both must stay byte-identical so Codex CLI, generic agent runners, and Claude all see the same gotchas, and CodeRabbit stops flagging `AGENTS.md` drift as PR noise (CR's `--base main` scan picks up working-tree drift on every unrelated PR). Any edit to `CLAUDE.md` needs a paired `cp CLAUDE.md AGENTS.md && git add CLAUDE.md AGENTS.md` in the same commit. If divergence is ever intentional (agent-tool-specific content), document why at the top of `AGENTS.md`.
- **New prompt files (anything fetched via `chrome.runtime.getURL()`) MUST be added to `manifest.json` → `web_accessible_resources.resources`.** Missing entry → `getURL()` silently 404s; `loadBasePrompt()` / `loadLandingPrompt()` / `loadVoicePrinciples()` fall back to inline defaults or empty strings depending on the call site, and the analysis quietly degrades. `tests/manifest.test.js` iterates resources and validates files exist, but the "files exist" check only flags missing-on-disk — to detect missing-from-manifest you need an explicit `expect(promptResource.resources).toContain("...")` per new prompt file. PR [#59](https://github.com/sumrae412/toneguard/pull/59) added the explicit `voice-principles.txt` assertion after the gotcha surfaced.
- **`tool_use.input` can contain text-format function-call markup leaked into string fields — JSON parses fine, contents are corrupted.** Anthropic's text-format function-call markup (`<parameter name="...">...</parameter>`, `<invoke>`, `<function_calls>`) occasionally bleeds from the next tool argument into the current argument's string value. The JSON envelope is valid; only the string content is corrupted. Inverse of the TG_PARSE_001 class (which is malformed-JSON), so `extractToolResult` / `extractPwaToolResult` pass the corrupted payload straight to the UI. Fix in [PR #63](https://github.com/sumrae412/toneguard/pull/63): `validateToolInput()` + `hasToolCallXmlLeak()` + `TOOL_CALL_XML_LEAK_RE` in `lib.js`, mirrored in `sync-server/pwa/app.js`. Per "Never swallow parse errors into a destructive default" — return null so the existing escalation surfaces a clean failure. Follow-up: `toneguard-mcp/analyzer.py` has the same shape via `_extract_tool_result` (dev/CI only, not user-facing — deferred).

- **The store zip must include every file `manifest.json` references — verify with a zip-vs-manifest diff before any store upload.** `npm run build` omitted `overlay.html` + `overlay-frame.css` + `overlay-frame.js` (all `web_accessible_resources`); unpacked dev installs worked, a packaged store install would have broken at runtime ([PR #86](https://github.com/sumrae412/toneguard/pull/86)). Recipe: script that diffs zip contents against every manifest-referenced path. Related: Chrome cannot install a raw zip at all — cross-machine installs are Load-unpacked from the unzipped folder (or the store build).
- **Passed messages show only a small toast — UI polish on the analysis flow is invisible unless your test message FAILS.** When verifying overlay/drawer changes, use a message that reliably triggers a flag (escalation phrases like "Are you serious? Per my last email..." route deep deterministically); a borderline 5-word message passing is normal model variance, not a broken analyzer (and the user's own "send as-is" decisions feed back as learning patterns, shifting future verdicts).
- **A restyle pass must apply the full polish layer to BOTH light and dark variants** — a palette hue-swap on the dark drawer left it structurally stale while light mode got spacing/typography polish (user: "sidebar still looks like this", [PR #84](https://github.com/sumrae412/toneguard/pull/84)). The append-only "polish layer" CSS block before `</style>` (cascade wins, zero selector changes) works, but must be authored per color scheme.
